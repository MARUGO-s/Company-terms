# 来客・売上予測と事前予測の精度評価

2026-09-10 / `forecast-audit-v1`。数値予測の現行仕様。以前のGLM自動選択・全履歴MAPEの説明に優先する。

## 目的と限界

MARUGO Sの仕入れ・人員配置の判断に使う客数・売上予測を、将来の実績で検証して改善する。「最高精度」「蓄積すれば必ず改善」「80%必ず的中」とは保証しない。数か月の実績から年間季節性や複雑な非線形トレンドを断定しない。

旧画面の約20ptの上下は、GLMと乗算モデルの切替と表示指標の不一致を含んでいた。日別の実際の予測誤差そのものではなく、台風による因果関係をこの表だけから判断できない。MAPEは確率でも予測区間でもない。

## 発行と保存

- 既存 `foodcourt-forecast-cron` が通常JST05:00に実行。共通cron認証を維持する。
- `foodcourt_base_daily` の発行日より前の完了実績だけで学習する。28有効日未満はスキップ、最新実績が3日以上前なら409で止める。未入力・負数・客数0なのに売上が正の行は除外し件数を残す。客数・売上がともに0の実績は保持する。休業と未記録を自動で同一視しない。
- 特徴量・実績・台帳をページング取得する。各予測に使う学習は直近365有効日まで。予測入力は曜日、会場別イベント、降水量、猛暑、天候不明フラグ。未取得の天候を晴れの確定値にしない。
- 事後に取り込まれる実測観客数を予測変数に使わない。イベント・天気の現在の値と出所・更新日時を発行時に保存する。
- 当日〜14日先、5方式×15対象日の75予測を同時発行。`foodcourt_forecast_issuances` は店舗・JST発行日で一意、`foodcourt_forecast_snapshots` は発行ID・対象日・方式で一意。
- `publish_foodcourt_forecast_v2` はservice_role専用、MARUGO S固定、DB時刻と学習締切を検査。advisory transaction lock下で台帳・最新予測・係数・履歴を一括保存する。途中失敗は全ロールバック。同日再実行は最初の成功を保持する。
- 新台帳はRLS有効、anon/authenticated権限なし。service_roleも直接INSERT/UPDATE/DELETE不可。UPDATE/DELETE拒否トリガを持つ。将来の実績訂正は実績側へ反映し、予測は書き直さない。
- `forecast_predictions` は既存の画面・AI向け最新表示キャッシュとして継続。過去のpredictedは再計算で上書きせずactualだけ照合更新する。精度の正本には使わない。
- 手動等でJST09:00以降に発行した予測も保存・表示するが、`evaluation_eligible=false` として朝の事前予測の採点・自動切替から除外する。

## 5つの方式

| ID | 方式 |
| --- | --- |
| `mult-factor-v4-safe` | 現行乗算方式に天候不明の周辺化・観測済み天候だけの係数推定・ゼロ実績への対応を追加した初期採用モデル |
| `weekday-4-v1` | 直近4回の同曜日平均。全候補が勝つべき単純基準 |
| `similar-days-v1` | 曜日・イベント一致、降水量の近さ、42日半減の重み付き類似日平均 |
| `ridge-direct-v1` | 客数・売上を別々に予測する正則化回帰。56日半減、曜日・イベント・降水量・猛暑・天候不明。正則化4固定 |
| `ensemble-v1` | 同曜日・類似日・正則化回帰の等重み平均 |

新しい方式だから有利に扱わない。予測ロジック・定数を変更したらIDも更新し、別モデルとして台帳に蓄積する。追加時はRPCの方式数・ID検査、テストも変更する。GLMの短期勝敗による日々の切替は廃止した。

## 公平な採点と採用

画面の主評価は「本番・事前予測 / 直近28日 / 1日前」。14日は警戒用、56日は参考。0・1・7・14日前を選択できる。発行時刻・学習締切・対象期間・評価日数を併記する。

- WAPE: 絶対誤差合計÷実績合計。ゼロ実績日の誤差も分子へ加算する。実績合計0なら評価不能。
- MAE: 平均で何人・何円ずれたか。
- 偏り: (予測−実績)合計÷実績合計。プラスは過大、マイナスは過小。
- MAPE: 実績が正の日だけの補助指標。母数とゼロ実績日数を保持する。150%超も正しい割合として表示。
- 同曜日比: 同じ対象日のペアだけで比較したMAEの相対改善率。MASEとは呼ばない。雨天・雨なし・天候不明・イベントあり/なしも各母数とともに記録する。
- 予測幅: 同じ方式・同じ先行日数の既知の絶対誤差から求める経験的80%幅。事前予測の確定実績20日未満は、過去再計算20日以上があれば参考幅として使う。それも不足ならnull。的中率は本番台帳に保存した区間と後日の実績でのみ評価する。時系列依存・予報誤差があるため80%保証はしない。

自動切替は月曜のみ。直近28暦日の1日前事前予測を使い、現行・候補・同曜日基準の共通21日以上が必要。客数と売上のMAEがともに現行より5%以上改善し、前後半（各7日以上）でも両方改善すること。複雑な候補は同曜日基準にも両方勝つこと。採用後28日は再切替を待つ。これは安全策であり、有意差検定や将来の勝利の保証ではない。判定理由を保存する。

過去再計算は拡張窓・最低28日学習・発行日以後の実績を除外して各先行日数を再現する。ただし天気・イベントは現在の更新済み値であり、本番精度の証拠には使わず、方式選択へ渡さない。2026-09-10時点の直近28日参考検証では、乗算方式の売上WAPE19.5%、同曜日基準28.2%。これは当時発行した予測を検証した数値ではない。

## 画面・API・AIへの表示

`admin-api /foodcourt/evolution-history` は既存認証・店舗スコープのまま `forecast_audit` を返す。公開HTMLから業務テーブルへ直接アクセスしない。概要に5方式比較・事前予測と再計算の選択・将来予測一覧を表示。学習曲線と全記録は参考再計算と明示し、方式・評価バージョン変更を改善/悪化とは扱わない。旧UIに残っていた固定サンプル精度・レベル・信頼度星は廃止。

AI解説の乗算係数は解釈用であり、採用方式の因果説明と同一視しない。予測一覧の混在MAPEも参考集計と明示。AI回答/RAG品質の点数設定は数値予測の採用条件と独立。

## 運用と検証

- migration: `20260910140000_foodcourt_forecast_issuance.sql`。都市対抗等の特定タイトルを持つドームイベントの誤ったプロ野球分類も補正。公式パーサとAI抽出後の保存時に同じ補正を適用する。
- `dry_run=1`: 認証は通常と同じ。学習・予測・評価・データ品質を返し、DBへ発行しない。
- `npm run test:foodcourt`: 時系列の未来混入、ゼロ/欠損、曜日基準、候補比較、切替の前後半・冷却期間、イベント分類、PGliteによる実SQL適用・認可・部分失敗ロールバック・再実行・改変拒否を検証する。
- ローカル画面は `PORT=8796 ./scripts/local-line-report-pages.sh`。PC/390px幅、評価種類・期間・先行日数、モデル切替表示、180%MAPE、未認証非表示を検証。
- 本番では台帳の初回発行、75スナップショット、二重実行時の件数不変、採用モデル、401、Advisorsを確認する。初日は評価母数0が正常。朝の1日前予測の確定実績が21日以上集まるまで自動昇格しない。
- この仕組みだけで台風の因果は確定できない。休業・営業時間短縮、警報、交通影響の発行時点データが必要。祝日・予約・告知等も、事前取得できるデータを追加して新IDの候補で検証する。

方法の参考: [rolling-origin evaluation](https://otexts.com/fpp3/tscv.html)、[forecast accuracy metrics](https://otexts.com/fpp3/accuracy.html)。
