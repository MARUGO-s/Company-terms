# フードコート 来客・売上予測 学習システム構造

更新: 2026-09-10。本番反映済みの `forecast-audit-v1` を説明する。詳細な採点・採用条件は [FOODCOURT-FORECAST-AUDIT.md](./FOODCOURT-FORECAST-AUDIT.md) が正本。データ増加だけで精度向上を保証しない。

## 1. 全体の流れ

```text
LINEテナント一覧 → foodcourt_tenant_reports → foodcourt_daily_facts
精算レシート・手入力客数 → foodcourt_base_daily（基準店の確定実績）
イベント取得 → tokyo_dome_events ┐
天気取得     → weather_daily     ┴→ foodcourt_daily_features
                                    ↓
完了実績（発行日より前）＋発行時点のイベント・天気
    ↓ 毎朝05:00 JST、5方式で当日〜14日先を計算
改変不可の発行台帳・75予測（5方式×15日）
    ↓ 後日の確定実績と照合
本番評価：同じ対象日・方式・先行日数でWAPE/MAE/偏りを計算
    ↓ 月曜のみ、共通日数・改善幅・前後半・冷却期間の条件を検査
条件を満たした候補だけ採用／不足なら現行方式を維持
                                    ↓
最新予測キャッシュ → 既存分析画面・AI解説
発行台帳の評価     → AI学習・進化画面
```

## 2. 入力と学習範囲

- テナント一覧は保存後に日次factsへ正規化する。数値予測の教師データは `foodcourt_base_daily` の基準店 MARUGO S の完了実績。
- 発行日当日・未来の実績を学習に入れない。各候補は直近365有効日までを使う。28有効日未満は発行せず、最新実績が3日以上前なら409で停止する。
- 未入力・負数・客数0かつ売上が正の不整合行は除外し、件数を記録する。客数・売上とも0の実績は保持する。未入力を休業扱いしない。
- 曜日、会場別イベント種別、降水量、猛暑、天候不明を使う。将来のイベント・天気が必ず揃うとは限らない。天候不明を晴れとみなさず、入力と出所・更新時刻を発行時に保存する。
- 動員の入力・保存・AIの背景分析は継続するが、事後取得の実測動員を現行5方式の数値予測へ混ぜない。入力日数が増えれば必ず精度が上がるという仕様ではない。

## 3. 5方式と安定した採用判定

毎朝計算するのは、安全補正乗算（`mult-factor-v4-safe`）、直近4回同曜日（`weekday-4-v1`）、類似日（`similar-days-v1`）、客数・売上別の正則化回帰（`ridge-direct-v1`）、3候補の等重み平均（`ensemble-v1`）の5方式。初期採用は安全補正乗算で、比較候補の予測も同時保存する。

主評価は朝の1日前予測・直近28暦日。月曜日に、現行・候補・同曜日基準の共通21日以上で客数と売上のMAEがともに現行より5%を超えて改善し、前後半（各7日以上）でも両方改善することを確認する。同曜日基準以外の候補は同曜日基準にも両方勝つ必要がある。採用後28日は再切替を待つ。条件未達なら現行方式を維持する。

再計算は最大56日・各先行日数について、仮の発行日より前の実績だけで学習する。ただし天気・イベントは更新済み値なので参考であり、本番精度や採用判定には使わない。GLMのλ探索、年間季節性・二次トレンド、毎晩のバックテスト勝者への切替は旧方式。

## 4. 保存先と役割

| テーブル・ビュー | 役割 |
| --- | --- |
| `foodcourt_base_daily` | 基準店の確定実績。学習・後日の採点に使用 |
| `foodcourt_daily_features` | 曜日・イベント・天候を日付で結合 |
| `foodcourt_forecast_issuances` | 店舗・JST発行日で一意の発行情報、締切、採用方式、評価、品質情報 |
| `foodcourt_forecast_snapshots` | 発行ID・対象日・方式で一意の75予測。入力・客数/売上・上下限を固定 |
| `forecast_predictions` | 既存画面・AI用の最新表示キャッシュ。過去予測は上書きせず実績だけ更新。精度の正本ではない |
| `foodcourt_forecast_factors` | 解釈用の乗算係数、統計拡張、最新の採用判断 |
| `foodcourt_forecast_history` | 参考再計算の履歴。新方式は最大56日・1日前、`evaluation_version`付き |

`publish_foodcourt_forecast_v2` が固定店舗・DB時刻・学習締切・75件の形式を検査し、ロック下で全出力を原子的に保存する。途中失敗は全ロールバック。同日再実行は最初の成功を保持する。台帳は直接更新・削除できない。

## 5. 表示と精度の読み方

- [AI学習・進化](https://marugo-s.github.io/line_report/foodcourt-evolution.html) の「本番・事前予測 / 直近28日 / 1日前」が主評価。期間14/28/56日、先行日数0/1/7/14日を選択できる。
- WAPE、MAE、過大/過小の偏り、同曜日基準との同日比較、条件別母数、区間的中率を確認する。MAPEは補助指標で、確率・予測幅ではない。
- 予測幅は同じ方式・先行日数の絶対誤差から作る経験的80%幅。本番の確定誤差20日未満なら参考再計算へ切り替え、その旨を表示。どちらも不足なら幅は未評価。
- 学習曲線・全記録は参考。方式・評価バージョン変更時は「評価条件切替・比較不可」と表示する。
- `GET /foodcourt/evolution-history` が `forecast_audit` と採用方式の15日分を返す。業務データは既存認証・店舗スコープ付きAPIだけから読む。
- 解釈用乗算係数は、他方式を採用したときの計算根拠そのものではない。AI回答の品質点と数値予測の採用条件も別。

## 6. 自動実行・確認

予測ジョブは `foodcourt-forecast-cron-job`、`0 20 * * *` UTC＝毎朝05:00 JST。2026-09-10にactiveを確認した。他の収集ジョブの時刻は実際のcron設定を確認し、予定どおりの取得を仮定しない。

- `?dry_run=1` は通常と同じcron認証が必要。DBへ発行せず、計算結果・評価・品質を点検する。
- JST09:00以降の手動発行は保存するが、朝の本番評価には混ぜない。
- 初回本番発行は2026-09-10の夜間、75件。翌朝以降の事前予測と後日の実績を蓄積する。初日の評価母数0・「蓄積中」は正常。
- DB・API・Pagesの配備、二重実行時の件数不変、未認証401を確認済み。証跡は正本の本番反映節を参照。

## 7. 今後追加するデータ

休業・短縮営業、警報、交通影響、祝日、予約、告知などは、発行前に取得した情報として時刻付きで保存できるかを先に確認する。未実装の補正を既存予測にあるものとして説明しない。新モデルIDで事前評価し、改善を検証してから採用する。
